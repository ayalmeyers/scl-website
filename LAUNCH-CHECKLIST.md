### Round 5 (follow-up)

- **Built the full QA harness** (`npm run qa`, `package.json` + `qa/run.js`): serves the repo locally, drives every page in headless Chromium at three viewports, and checks console errors, broken local resources, horizontal overflow, and accessibility via `@axe-core/playwright` (WCAG 2.0/2.1 A + AA). Writes `qa/report/report.json` and a pass/fail summary; exits non-zero on failure, so it's CI-ready. `npm run qa:lighthouse` adds Lighthouse performance/accessibility/best-practices/SEO scores as a separate opt-in command — Lighthouse launches its own Chrome, and that launch reaches a few Google hosts on startup, which this session's sandboxed egress proxy blocks (the launch hangs rather than failing fast, confirmed by direct reproduction outside the harness too). It should run fine in a normal CI runner or on a laptop; this pass could not get Lighthouse scores for that reason, which is an environment limitation, not a code issue.
- **Caught and fixed a bug in the harness itself before trusting its output**: the first draft only paused 40ms between scroll steps before running the axe-core accessibility scan, but this site's `.reveal` scroll-in elements fade in over a 0.9s CSS transition (plus up to a 0.34s stagger). That caught elements mid-fade and axe correctly, but misleadingly, reported low color contrast for that instant — 18 of the 20 initial "violations" were this false positive, confirmed by directly inspecting computed opacity mid-transition (e.g. one flagged element's ancestor was at `opacity: 0.73` when sampled, not yet settled to 1). Fixed by waiting long enough per scroll step and settling fully before the scan; re-ran and confirmed the false positives disappeared.
- **Fixed the two real, static contrast bugs the (corrected) harness found**: the header nav links (`.nav-links a`, including "Contact Us") were set to `opacity: 0.62`, which cleared AA contrast against the page's white background but fell to 4.29:1 (short of the 4.5:1 minimum) against the header's own `#ecedf0` tint once scrolled. Raised to `0.68` — comfortable margin confirmed against both backgrounds. Separately, the breadcrumb "← Musings" links on all 6 article pages had both insufficient color contrast against their surrounding text *and* no non-color distinction (no underline) — a `link-in-text-block` violation. Added an underline.
- **Confirmed one further flagged item is a deliberate, accepted design tradeoff, not a bug**: the homepage's "Coaches / Counsel / Consultants" flow-scroll cards intentionally fade non-centered cards via inline `opacity` as part of the spotlight scroll effect Ayal specifically asked for and approved earlier in this engagement — the same way a carousel's inactive slide is expected to read as visually de-emphasized. This is the one remaining `npm run qa` failure on a clean checkout; left as-is rather than altering the motion effect on my own judgment (consistent with Round 2's decision to leave this actively-iterated effect alone). Documented in `README.md`'s "Running QA" section so it isn't mistaken for an unfixed bug later.
- Verified the whole harness end-to-end: full regression sweep (all pages × 3 viewports, console/network/overflow) and the existing roster Playwright test both still pass clean after the two CSS fixes above.

### Round 4 (follow-up)

- **Built the headshot-normalization pipeline**: `scripts/normalize-headshot.sh <input> [output]` (ImageMagick) re-encodes a photo to a consistent JPEG quality (85) and color space (sRGB), strips all embedded metadata (EXIF/ICC/XMP — camera and sometimes location data had no business shipping to site visitors), auto-corrects orientation, and caps the longest edge at 1280px (2x the largest size any headshot is ever displayed at: the bio dialog photo, `min(92vw, 640px)` wide). It's a repeatable script, documented in `README.md`, meant to be run on any new or replaced team photo going forward.
- **Ran it on all 7 current team headshots.** Source files varied wildly — square, portrait, even one landscape; quality settings from 80 to 99; one (`JimZarvos.jpg`) carrying ~23KB of embedded profile/EXIF data for a 576×864 photo. Normalizing brought total size for the 7 headshots from 729KB to 385KB (47% smaller), with the worst offender (`JimZarvos.jpg`) dropping from 346KB to 58KB. No photo was re-cropped or re-composed — only re-encoded — so how each person is framed is unchanged.
- Added `photoWidth`/`photoHeight` to each person's entry in `team.js` (the post-normalization pixel dimensions) and wired them into `renderTeam()`'s three `<img>` renders (homepage teaser, roster card, bio dialog) as explicit `width`/`height` attributes, so the browser can reserve the right space before the image loads.
- **Also ran it on the four other oversized site photos** that showed the same bloat pattern (`01.jpg`, `02.jpeg`, `03.jpg`, `leader-portrait.jpg` — the "Coaches/Counsel/Consultants" pillar photos and a video poster). `01.jpg` dropped from 252KB to 84KB, `03.jpg` from 310KB to 49KB (both were quality-99 JPEGs with no reason to be). `02.jpeg` and `leader-portrait.jpg` were already reasonably encoded and came out roughly flat. Did not touch their resolution otherwise (see "upscaling" note below — that's a separate, decision-blocked issue, not something compression fixes).
- Verified with: `node --check` on `main.js`/`team.js`, the existing roster Playwright test (grid rendering, dialog open/close, bio content, deep-link-on-fresh-navigation all still correct), a full regression sweep (all pages × 3 viewports, console/network/overflow — clean), and before/after screenshots confirming no visible quality loss on any of the 11 re-encoded images.
- Updated `README.md`'s "Editing the roster" section (it was stale — written before the Round 3 `team.js` refactor landed, still describing hand-duplication that no longer exists) and added a "Headshots" section documenting the new script.
